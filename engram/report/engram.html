Engram: long-term context for a coding agent, in one Strata file

A coding session on a large project outlives its context window many times over. Engram stores everything Claude Code does through its hooks, finds what matters again with Strata's hybrid search, and decides on its own when to put it back into the prompt. The model can also search its history when it decides to. This page is the design, the implementation, and an evaluation on two long-conversation benchmarks, on the 26-hour session that built this repository, and in live Claude Code runs.

The problem

A context window is working memory. Long projects need a long-term memory that fills itself, and that is consulted only when it has something to say.

When a Claude Code session nears the end of its context window, it compacts: the history is replaced by a summary of about 15,000 characters. That keeps the plan and drops the particulars, such as the exact error, the number a decision rested on, or a preference stated once. A new session starts with only CLAUDE.md and an index of notes.

Reading more history is not the fix. On LongMemEval, GPT-4o answers 87% of questions when given only the relevant sessions, but 61% when given the whole 115,000-token history. A memory has to retrieve, and it has to retrieve selectively: in coding-agent experiments, an irrelevant memory lowered the solve rate below having no memory at all (26% with none, 22% with the wrong one).

So there are two decisions to make on every event, and the model should not have to make either one deliberately:

  • When to store: always, because storage is cheap and a missed record cannot be recovered. What varies is granularity and salience.
  • When to load: only when the evidence is strong, only within a small budget, and never for what is already in the window. The model can still pull more through tools when it knows it needs to.

Architecture

Strata takes an exclusive lock on its file, and hooks are short-lived processes that may run alongside the MCP server. So one daemon per project owns the store, and every hook and MCP call is a client on a Unix socket. The first client starts the daemon, which exits after 30 idle minutes. A client that cannot reach it in time prints nothing and exits 0, so memory never blocks a prompt or a tool.

Each record is one row of a Strata table: the text, an indexed context column, and fields for kind, session, sequence number, time, files and a 512-dimensional vector. The context column holds the request of the turn a tool result belongs to, or the section a summary chunk came from. A generated column indexes the text and its context together, so a tool output can be found by what the user was asking at the time. This follows LongMemEval's finding that expanding a record's index key works only when the expansion is indexed with the record.

When to store

Always, from the hook payloads. Nothing depends on the model deciding to save:

UserPromptSubmit

The prompt, plus a preference record for each sentence with a lasting rule ("always", "never", "from now on").

PostToolUse

The call and its result. Failures become error records. Long output is chunked and trimmed to its head and tail; Read results become stubs, since the file is on disk.

Stop

The final answer, the commentary written between tool calls (read from the transcript tail), and an episode card: prompt, files changed, commands, errors, outcome.

PostCompact

Claude Code's own summary, split by section. Pending tasks become todo records, and the live window restarts here.

Each kind carries a salience prior \(\iota\): preference 1.0, decision 0.9, summary and facts 0.8, prompts 0.7, errors and episodes 0.6, answers 0.5, tool calls and results 0.3. Replaying the 26-hour session through this capture gives 1,833 records up to the start of this task, and 2,204 for the whole transcript. The model can add durable knowledge itself with memory_remember, and mark older records as superseded.

When to load

Records still in the model's context are never injected. For session \(s\), the daemon keeps the window start \(w_s\): the sequence number at session start, or at the last compaction. Every recall excludes

\[ \{\, r : r.\mathrm{session} = s \,\wedge\, r.\mathrm{seq} \ge w_s \,\} \;\cup\; \mathrm{injected}_s . \]

There are three automatic load points and one pull path:

  • Session start, resume and compaction: a briefing of at most 2,500 characters. It covers stated preferences, recorded decisions, open tasks from the last summary, and where the previous session stopped. After a compaction it also recalls what is relevant to the last two prompts.
  • Every prompt: gated recall, described below.
  • Before Edit or Write: up to two earlier errors, decisions or episodes about that file, once per window.
  • Pull: the MCP tools memory_search, memory_timeline and memory_sql.

Ranking

BM25 over the text and its context, and cosine similarity over the vectors, each return their top 50 through Strata. Scores are min-max normalised over the union, with a missing score counting as 0. Priors break near-ties without overriding relevance:

\[ \mathrm{rel}(r) = w\,\widehat{\mathrm{bm25}}(r) + (1-w)\,\widehat{\cos}(r), \qquad S(r) = \mathrm{rel}(r)\bigl(1 + \lambda_\iota\,\iota(r)\bigr) + \lambda_t\, e^{-(\mathrm{seq}_{\max} - \mathrm{seq}(r))/\tau}, \]

with \(w = 0.5\), \(\lambda_\iota = 0.2\), \(\lambda_t = 0.05\) and \(\tau = 5{,}000\) records. Packing takes records by \(S\), at most two per turn so that more distinct evidence fits. Each record is cut to the 600 characters around the query's terms. The packed records are shown oldest first, each with its id, time, session, turn and kind, and labelled as possibly outdated. After them come up to five further candidates, one line each (id and opening words), which the model can open with memory_timeline.

Two kinds of record are never candidates:

  • Answers that admitted not knowing ("I don't know…"), which are stored with low importance and tagged.
  • Earlier copies of the question being asked.

Both match a repeated question best and carry nothing, so recalling them would only repeat the failure. The live tests below show why this matters.

The gate

Normalised scores cannot gate, because the best candidate always scores 1. The gate uses absolute evidence about the best candidates:

  • the highest cosine, and how far it stands above the tenth (\(\Delta_{\cos}\));
  • the highest IDF-weighted share of query terms a top-5 record contains;
  • how far the best BM25 score stands above the tenth (\(\Delta_{\mathrm{bm25}}\));
  • whether BM25 and vectors agree on the top record;
  • whether the prompt refers back ("earlier", "we decided", "did we").
\[ G = a\,\cos_{\max} + b\,\mathrm{cov}_{\max} + c\,\mathbb{1}_{\text{cue}} + d\,\mathbb{1}_{\text{agree}} + e\,\Delta_{\cos} + f\,\Delta_{\mathrm{bm25}}, \]
\[ \mathrm{cov}(q, r) = \frac{\sum_{t \in q \cap r} \mathrm{idf}(t)}{\sum_{t \in q} \mathrm{idf}(t)}, \qquad \Delta_{\cos} = \cos_1 - \cos_{10}, \qquad \Delta_{\mathrm{bm25}} = 1 - \frac{\mathrm{bm25}_{10}}{\mathrm{bm25}_1}. \]

A logistic fit on LongMemEval gives the weights and the two thresholds: \(\theta_{\text{hi}}\) holds precision 0.9 and \(\theta_{\text{lo}}\) precision 0.7. In the fit, positives are questions whose evidence the packed injection contains; negatives are questions asked against another conversation's store, abstentions and misses.

Evaluation

The evaluation has four parts:

  • Retrieval: two public long-conversation memory benchmarks, scored by whether the injected text contains the evidence.
  • This repository's session: 26 hours, two compactions, three projects, asked what it had lost.
  • Systems: latency and storage up to a million records.
  • Live runs: headless Claude Code sessions with Engram installed.

The default embedder is static (Model2Vec potion-retrieval-32M): a token lookup and a mean, 512 dimensions, about 50,000 records a second on an Apple M2 laptop. BGE-small, a 33-million-parameter transformer, is the alternative; it took about 50 ms per short text on the 4-core cloud VM where it was measured.

Retrieval on long-conversation benchmarks

Each benchmark conversation becomes its own store, with one record per turn chunk, each indexed with its exchange partner as context. A question succeeds when its annotated evidence turn comes back.

  • LongMemEval-S: 500 questions, each over its own history of about 115,000 tokens; the 470 with evidence are scored.
  • LoCoMo: 10 conversations of about 600 turns and 1,536 answerable questions.

On LongMemEval-S, hybrid search with priors puts the evidence in the top 10 for 90% of questions, against 88% for BM25 and for static vectors alone. The default 4,000-character injection contains it for 87%. LoCoMo's short turns between two people favour exact words: BM25 alone reaches 0.651 at rank 5 and static vectors only 0.382, so the static hybrid (0.607) falls below BM25. BGE vectors reverse that, 0.548 alone and 0.678 in the hybrid, above BM25. On LongMemEval, BGE does not help: on every fifth history (94 questions) its vectors alone score 0.691 against 0.745 for the static model, and the hybrid 0.798 against 0.809. Its strength is paraphrase, which the session probes below show; its cost, measured on the cloud VM, is a few hundred times the static model's time per record.

By question type, hybrid search helps most on multi-session questions, which need evidence from several conversations: recall@5 rises from 0.760 with BM25 to 0.835. Preference questions are hardest, at 0.50. A question such as "can you suggest a hotel?" shares no words with the user's earlier statement of taste, and the static vectors do not bridge the gap either.

Indexing a record with its context is not free. On LoCoMo, adding the request to each turn raises recall@5 from 0.549 to 0.607. On LongMemEval it lowers it slightly, from 0.866 to 0.853, and to 0.832 if user turns also get the assistant's reply. Those answers are long, and the questions target the user's own words, so the extra text dilutes them. Engram attaches the request to responses only, which is the "with their request" column.

What this repository's session lost, and what came back

The transcript of the session that built this repository is the most realistic test available: 26.5 hours, 43.6 MB, three projects, and two compactions whose summaries keep 14,202 and 17,998 characters. Replaying it through Engram's capture gives the records the hooks would have stored. The questions are asked at line 5,392, just before this task began. At that point the model's context is the second summary plus everything after it.

There are three probe sets:

  • Recurring facts (40): questions about decisions and results that later work kept restating.
  • Lost details (18): questions about errors, failed commands and measurements that no later text repeats, found by searching the transcript for lines absent from the later context.
  • Lost details, vague (12): the same details, asked the way someone would who no longer remembers the identifiers.

The lost-detail questions were written after seeing their answers, so they favour exact terms; the vague set measures how much that matters.

After a compaction, the summary held none of the lost details, and the live window still held 17% of them. Of the 15 the model no longer had, automatic injection brought back 13, and one memory_search 14. Asked vaguely, injection recovered 8 of 10. Recurring facts were mostly still in context (84%), so Engram had little to add there: 2 of the 5 missing ones came back automatically, and all 5 by search.

A new session is where memory matters most, because it starts with nothing. There, the gated injection alone answered 83% of the lost-detail probes, 58% of their vague versions and 54% of the recurring facts; search raised these to 94%, 67% and 78%. Most answers that search found but injection missed came through the weak-evidence tier. It injects two records of at most 500 characters, and the answer ranked first to eighth but fell outside those records or their snippets. The injected record ids are what the timeline tool is for.

With BGE vectors, raw retrieval improves where the words differ. In a new session, full injection would contain 28 of the 37 recurring-fact answers, against 23 with the static model, and search would find 31, against 29. The BGE gate costs more than it gains, though. Fitted on fewer questions, it rarely reaches full injection, so its gated injection recovered only 4 of the 10 vague lost details, against 8 with the static default. The static embedder with its gate stays the default.

The gate

The gate is the weakest part of the design. Fitted on LongMemEval, it compares as follows with injecting the full budget on every prompt:

  • Cost: it injects on 55% of prompts, about 930 characters per prompt against about 3,000.
  • Precision: injections that contain evidence rise from 42% to 59%.
  • Coverage: questions whose evidence reaches the model fall from 87% to 67%.
  • LoCoMo: on this held-out benchmark it saves the same tokens but loses precision, because its foreign questions share too much vocabulary with the stores they are asked against.

With BGE vectors the same fit fares worse: its full-injection threshold is reached by about 1% of questions, so nearly everything goes through the brief tier. In practice, the gate mostly limits cost. The features it has, similarity and term coverage, cannot tell "related" from "relevant" well. A cross-encoder reranker on the top candidates is the obvious next step; in this design its cost would fall only on prompts that pass the cheap gate.

Scale and latency

How large does a project's memory get? The 26-hour session produced about 2,200 records, so a million records is roughly 450 sessions of that size, more than a year of daily heavy use. The scale test fills a store with LongMemEval turns and asks about needles in it:

  • Needles: 94 questions whose evidence sessions are kept.
  • Filler: generic chat sessions without evidence, repeated to reach 10,000, 100,000 and 1,000,000 records.
  • Order: sessions are shuffled, so recency favours neither.
  • Hooks: run through the real engram binary and daemon, one prompt every 200 ms.

The costs grow slowly. A recall query takes 1.3–1.7 ms up to 100,000 records and 5.7 ms at a million (p99 16 ms), about twice as fast as on the cloud VM this study first ran on (11.5 ms at a million). A full hook, counting process start, the socket round trip and gated recall, takes 14–16 ms at the median up to 100,000 records and 26 ms at a million (p99 43 ms). About 10 ms of that is starting the hook process on macOS; on the Linux VM that cost about 3 ms, and full hooks took 9–17 ms. Appends are durable commits, and on macOS each one flushes the drive's write cache (F_FULLFSYNC): 4.1–4.8 ms at the median and under 8 ms at p99, against 0.3 ms with fsync on the VM. Each record takes about 3.1 KB on disk, mostly its 512-dimension vector, and the static embedder processes 48,000–52,000 records a second (9,500–11,000 on the VM). The first hook of a session pays for starting the daemon: 50–72 ms in the latency study, about half of it opening the embedding model. In the table, where the first hook is a prompt that also recalls, it takes 75–97 ms; the run's very first daemon start, at 10,000 records, took 0.5 s.

Quality is what degrades. The share of needles found in the top 10 falls from 0.80 at 10,000 records to 0.65 at 100,000 and 0.44 at a million. Records are now cut at 400 characters, so these stores differ slightly from the first run's, which gave 0.78, 0.52 and 0.45. The filler here is chat on every subject, and real project history is more homogeneous, so this is a stress test, not a forecast. For large stores, Strata's filters keep the candidate set small: by session, time, file and kind. memory_sql gives the model those filters directly.

The hooks here arrive 200 ms apart. Back to back, each query waits for the previous write's in-memory segment rebuild; on the cloud VM a hook then took 44–53 ms. On the M2, with the current memtable (256-record chunks that scan their vectors), a query right after a write takes 6.35 ms at a million records (p99 16.2 ms), against 18.2 ms (p99 44.5 ms) with the earlier chunks that built an HNSW graph, whose rebuild takes about 12 ms. In a real session, prompts arrive seconds apart.

Live Claude Code runs

The last test is Claude Code itself, headless (claude -p, a small model), in a scratch repository after engram install.

  • Run A states two decisions and writes code. The hooks stored 12 records: the prompt, a preference picked up from "always", tool calls and results, the commentary, the answer and an episode card.
  • Runs B and C are new sessions with every file tool disabled, asking for the two decisions, with Engram on and off.
  • Run D asks for a detail the briefing does not carry.

With Engram, the new session answered from the briefing and said it had not checked the code. Without Engram, it said it did not know.

In run D, the model looked up the record id named in the injected context and called memory_timeline on it. It then quoted the exact command and output from the earlier session. Its first attempt had failed, because headless mode needs permission for MCP tools; engram install now adds the rule. Engram had also stored that failed attempt's answer, and the next session saw it and corrected it. Memory keeps wrong conclusions as faithfully as right ones, which is why every injected record is labelled as possibly outdated.

claude -p /compact on run A fired PostCompact, which stored the summary as 9 section records. SessionStart then injected a 4,713-character briefing and recall into the compacted context. The four runs together cost $0.018.

The final test asks a live session about this repository's own history. The 26-hour transcript, cut just before this task began, is back-filled into a fresh scratch project with engram ingest-transcript, giving 1,835 records. Four questions follow, each in a new headless session with file, shell and web tools disabled: two lost details, one design rationale and one result. Each question is asked twice, so the second round finds the first round's turns in memory, and once more with Engram off.

The questions and answers are not published: they quote a private development session.

With Engram, all eight answers were right. Two came from automatic injection alone. In the other six, the injection pointed the model at the right records, and it searched or opened a timeline before answering. Without Engram, the model could not answer any of the four.

Two earlier versions of this test failed in instructive ways.

  • An instruction suppressed the memory tools. When every question began "Without reading any files or running commands", the model took that to cover memory search too, and answered only two of four.
  • Old failures were replayed. Its "I don't know" answers were then stored and recalled by the next session as evidence that the answer was unknown. Engram now tags answers that admit not knowing, never injects them, and skips earlier copies of the same question. It was the second round of the clean run that checked this fix.

Verdict

Engram works as a long-term memory for Claude Code. Every hook event is stored without the model's help. The details compaction throws away come back when a prompt asks for them, and a new session starts out knowing what earlier sessions decided. Its weak point is the decision to inject: the gate keeps costs down but cannot reliably tell a related record from a relevant one.

Store without being asked

Met: prompts, tool calls and results, errors, answers, the commentary between tool calls, and compaction summaries are all captured from hooks. A hook costs 14–26 ms, about 10 ms of it starting the process on macOS; appends take 4–5 ms, because each commit flushes the drive's cache; and nothing blocks when the daemon is down. The 26-hour session becomes 2,204 records, back-filled in 6 seconds on the cloud VM.

Missed: the model's reasoning is redacted in transcripts, so the "why" survives only where it was written out. Commentary capture reads Claude Code's transcript, whose format is internal.

Load without being asked, only when it helps

Met: after a compaction, 13 of 15 lost details came back automatically. Live sessions answered all eight questions about this repository's 26-hour history, against none of four with Engram off. Nothing still in the context window is repeated, and answers that admitted not knowing are not replayed.

Missed: the gate's precision is modest: 59% against 42% for always injecting on LongMemEval, with no gain on LoCoMo. Vague questions recover less, 8 of 10 after compaction and 7 of 12 in a new session.

Let the model ask precisely

Met: in a live session, the model followed an injected record id with memory_timeline and quoted the exact command and output from the previous session. SQL over the memory table answers questions such as "the last errors in this file".

Missed: whether the model searches depends on the model and on the prompt. A "don't run commands" instruction stopped it from searching memory at all. Headless sessions also need a permission rule for the MCP tools, which the installer now adds.

Scale to projects far beyond a context window

Met: at a million records (about 450 sessions of this size), a recall query takes 5.7 ms at the median, a full hook 26 ms, and the file holds 3.1 KB per record.

Missed: finding one conversation's evidence among generic filler gets harder as the store grows: recall@10 falls from 0.80 at 10,000 records to 0.65 at 100,000 and 0.44 at a million, with the static embedder. Filters on session, time and file, and better vectors, are what keep large stores precise.

Limitations

  • The benchmarks are chats, not coding sessions. LongMemEval and LoCoMo test personal-assistant memory. The coding evidence is one long session and a handful of live runs.
  • The session probes were written after seeing the answers. They favour distinctive terms, which is why the vague set exists; real questions sit between the two.
  • The gate was fitted on chat data. Its weights depend on the embedder and probably on the domain.
  • The static embedder trades quality for speed. BGE is better on paraphrases, but it cost about 50 ms per record on the cloud VM's CPU.
  • Hook latency assumes a pause between prompts. Back to back, a query waits for the previous write's in-memory segment rebuild. On the cloud VM a hook then took 44–53 ms; on the M2, a query right after a write takes 6.35 ms at a million records (p99 16.2 ms), against 5.4 ms after the rebuild.
  • Redaction is pattern-based. It catches common key and token formats, not every secret.

Next steps

  • A reranker behind the gate. A small cross-encoder scoring only the top candidates of prompts that pass the cheap gate.
  • Two-speed embeddings. Capture with the static model, and re-embed in the background with BGE when the machine is idle.
  • Fact-augmented keys. One cheap model call per turn writes the turn's decisions and facts into the episode card's index text. LongMemEval reports about +9% recall from this.
  • Time-aware queries. Turn "yesterday" or "before the refactor" into time or sequence filters, which Strata already evaluates.
  • Consolidation. Detect when a new decision supersedes an older one, instead of relying on the model to say so.
  • Shared project memory. One store per repository, synced between teammates' agents.
